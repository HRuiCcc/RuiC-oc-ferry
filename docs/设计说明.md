# 设计说明

这份文档讲清 OC Ferry 是怎么工作的：进程怎么分、状态放哪、模型怎么被判定可用、以及 WorkBuddy 那边到底被写了什么。

## 一、它解决什么问题

WorkBuddy 支持在 `models.json` 里配置自定义模型（OpenAI 兼容的 `chat/completions`）。OpenCode 的免费模型池是现成的免费额度，但它不是一个可以直接填进 WorkBuddy 的 OpenAI 端点，而且：

- 目录里带 `free` 字样的模型不一定免费（要按**价格字段**判定）；
- 能聊天不等于能按 WorkBuddy 的方式**产生工具调用**；
- 免费池里的模型随时上下线，昨天的清单今天不算数。

所以需要一层适配：**发现 → 体检 → 导入 → 转发**。OC Ferry 就是这一层。

## 二、进程与数据流

```
Electron 主进程 (desktop/main.cjs)
  ├─ BrowserWindow ──preload(contextBridge)──> 控制面板 (renderer.js)
  │      ← state 推送            → window.ferry.action(name, value)
  ├─ Tray（菜单：动作 + 模型状态）
  └─ fork(src/main.js, ELECTRON_RUN_AS_NODE) ── 后台服务（也可 npm start 单跑）
         ├─ 占 127.0.0.1:41980
         ├─ 写 status.json（面板每 500ms 读它）
         ├─ 读/写 settings.json、probe-cache.json、api-key
         └─ spawn(隔离 OpenCode serve --pure)   ← 随机端口 + Basic 口令
                └─ /event 事件流（上游重试、审批、内容进度都从这里来）
WorkBuddy ──HTTP(Bearer)──> 127.0.0.1:41980/v1/chat/completions ──> 适配器 ──> OpenCode 会话
```

两个刻意的选择：

- **面板读文件，不读 IPC 流**：主进程每 500ms 读 `status.json`，只在 `pid` 与当前子进程一致时才接受。这一个判断同时挡住"读到上一次运行留下的状态"和"多实例互相覆盖"。
- **后台服务不依赖 Electron**：它只用 Node（`npm start` 能单跑），所以调试时不必拖着整个 GUI。

## 四、对外接口

### 本机 HTTP（`127.0.0.1:41980`）

所有路由都要 `Authorization: Bearer <数据目录>/api-key`；**任何带 `Origin` 头的请求一律 403**（这个端口不给浏览器用）。

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/health` | 完整状态（阶段、模型、版本、配置路径、代理开关） |
| GET | `/v1/models` | 只列**已判定可用**的模型，id 形如 `OC · <名字>` |
| POST | `/v1/chat/completions` | 转发（支持 `stream`）；并发上限 4，超出 429 |
| POST | `/admin/refresh` | 重读模型目录（会重启隔离 OpenCode） |
| POST | `/admin/probe` | `{model?}` 启动检测（显式动作，忽略判定缓存） |
| POST | `/admin/import` | `{modelsFile?}` 写 WorkBuddy 配置 |
| POST | `/admin/selection` | `{model, selected}` 勾选/取消 |
| POST | `/admin/system-proxy` | `{enabled}` 切换系统代理 |
| POST | `/admin/find-config` | Windows 自动查找配置 |

请求体上限 8 MB（413）；启动期返回 503；`requestTimeout 20s / headersTimeout 15s`，但**推理那条路 `setTimeout(0)`**——它自己持有取消信号，不靠这个超时。

### 数据目录

| 系统 | 路径 |
|---|---|
| macOS | `~/Library/Application Support/OC Ferry` |
| Windows | `%APPDATA%\OC Ferry` |
| Linux（实验性） | `$XDG_CONFIG_HOME/OC Ferry` |

文件：`api-key`（一次性随机密钥，0600）、`status.json`（完整状态，原子写）、`settings.json`、`probe-cache.json`（判定缓存）、`service.pid`、`opencode.log`（超 5 MB 轮转）、`runtime/<版本>/opencode`、`opencode/{config,data,cache,state,project}`。

环境变量：`FERRY_DATA_DIR`、`FERRY_PORT`、`FERRY_MODELS_FILE`、`FERRY_NO_SYNC=1`、`FERRY_OPENCODE_PATH`、`FERRY_PROBE_CONCURRENCY`、`FERRY_PROBE_TTL_MINUTES`、`WORKBUDDY_CONFIG_DIR`、`WORKBUDDY_DATA_FOLDER_NAME`。

## 五、WorkBuddy 配置契约

`models.json` 是**数组**或 `{ models: [...] }`。导入条目形状：

```json
{ "id": "OC · Big Pickle", "name": "OC · Big Pickle", "vendor": "Custom",
  "url": "http://127.0.0.1:41980/v1/chat/completions", "apiKey": "<本机密钥>",
  "supportsToolCall": true, "supportsImages": false,
  "supportsReasoning": true,
  "reasoning": { "supportedEfforts": ["low","medium","high"], "defaultEffort": "medium", "canDisableThinking": false },
  "maxInputTokens": 131072, "maxOutputTokens": 32768,
  "ocFerryOwner": "oc-ferry-v1" }
```

写入的六条安全阀：

1. 只增删带本产品归属标记（`ocFerryOwner: "oc-ferry-v1"`）的条目，**用户手写的一条都不动**；
2. id 查重：与用户自有条目同名（含客户端可见 id）就跳过，宁可少导一个也不覆盖；
3. 文件锁（`.oc-ferry.lock`，5 分钟视为过期）串行化写入；
4. 内容没变就返回 `changed:false`，不写文件也不产生备份；
5. 读写之间文件被别人改过 → 整体放弃，报 "retry refresh"；
6. 写前留备份（`.oc-ferry-<时间戳>.bak`，只保留最近 5 份）+ 原子替换。

**退出清理**：退出时先把自己的条目摘干净再停 OpenCode；异常退出留下的残留会在下次启动时被同一套合并逻辑清掉。

## 六、核心机制

### 6.1 免费模型怎么筛

看价格，不看名字：

```
cost.input === 0 && cost.output === 0 && cost.cache.read === 0 && cost.cache.write === 0
&& capabilities.output.text !== false && status !== 'deprecated'
```

### 6.2 检测：必须产生动作

给 5 个工具（`Read/Write/Bash/Glob/WebSearch`）、自由选择，让它"读取 `/external/probe-<随机 token>.txt`"，`parallel_tool_calls: false`，**60 秒预算**。判定分三类：

- 没有任何工具调用 → `no_action`：**不算失败**，按 **可用 · 仅对话** 发布（工具关掉）；
- 动作与请求不符 → `probe_mismatch`：**重试一次**（共用同一个 60 秒预算）；
- 格式装不下工具调用 → 降级为仅对话，但**必须再用一次纯对话确认它至少能聊天**；
- 超时与格式失败**都不重试**：超时反映负载，格式是确定性的。

目录里明说没有工具能力的模型**不浪费检测**，直接按仅对话发布。

### 6.3 检测并发与判定缓存（这一版的重点）

**并发**：串行等 11 个模型时，光两次 60 秒超时就够等两分钟。现在用 3 路并发（`FERRY_PROBE_CONCURRENCY`，上限 6），慢模型不再挡住快模型——实测一轮从数分钟降到约 60 秒。

**判定缓存**（`probe-cache.json`）：把"能不能按 WorkBuddy 的方式干活"这条结论跨重启留下来，重启后只为没判定过或判定过期的模型发请求（实测热启动 5 秒内完成、0 次请求）。

缓存有三种过期时间，按失败的性质分：

| 判定 | 保留 | 理由 |
|---|---|---|
| 成功 | 6 小时 | 免费池的可用性变化很慢 |
| 超时 / 限流 | 10 分钟 | 这是**当时的负载**，很快会自己好 |
| 已下线 / 无权限 / 额度用尽 | 1 小时 | 这是**关于这个模型的结论** |

另外两条规则：目录里同一个模型的能力声明变了（工具/推理/图片/上下文/输出上限），能力指纹对不上，缓存作废；模型从目录里消失就把它清出去。

**显式动作永远优先**：「检测全部」与「只重测这一个」忽略缓存，因为那是用户要求重新验证。真实调用成功了也会顺手刷新缓存的时间戳（刚用过就说明能用）。

### 6.4 信封协议：模型只回一个 JSON 对象

系统提示的硬约束（缺一条模型就会开始假装执行）：

- WorkBuddy 是唯一执行者；唯一可使用的本机工具是 `StructuredOutput`（只用来排版）；
- 只能从**本次请求带来的工具表**里选动作，名字与参数名逐字复制；
- 忽略 OpenCode 本机的环境与工作目录，路径只从外部对话里解析；
- 有依赖关系的操作不许放进同一个 calls 数组；
- 只回 `{"content":"...","calls":[{"name":"...","arguments":{}}]}`，不要 markdown 围栏；
- **返回的调用只是提议**，只有匹配的外部工具结果才算执行。

请求侧用 `format: { type: 'json_schema' }` 把 `calls` 的 schema **由本次工具表生成**：每个工具用 `name: { const: "工具名" }` 锁死，`tool_choice:none` 时数组上限归零。等于用 schema 把"能选什么"焊死。

响应侧接受三种等价抵达方式（结构化字段 / 已完成的 `StructuredOutput` 调用 / 纯文本），并把各家模型的写法归一化（`tool_calls`→`calls`、二次编码的字符串解开、`content:null` 补齐）。**但**：两个字段同时出现算含糊（拒绝），把调用摊平到信封上也算可疑——当纯文本收下等于静默丢掉那个动作。

### 6.5 审批围栏：本机动作一律拒绝或转交

会话级权限表把所有本机动作设为 `ask`，其余（question/websearch/webfetch/task/plan/todowrite）设为 `deny`。两条独立通路同时盯着：

1. **事件流**：工具 part 带着被拦下动作的名字与参数（HTTP 列消息查不到，这是唯一可靠来源）；`permission.asked` 维护待审批集合；`message.updated` 带 token 用量；`session.status` 的 retry 是上游重试唯一的可见处。
2. **审批轮询**（250ms）：与推理并行；**查询失败绝不等于批准**（退回事件流缓存），本机动作会一直停在等待。

拿到审批后：取回动作（最多等 4×120ms）→ 用静态映射表把本机工具名与参数名翻成外部工具的 schema（`bash→Bash`、`filePath→file_path`、`edit→Edit`…）→ **必填字段凑不齐就不转交**，回一条**点名工具与原因**的拒绝理由 → 转交成功就中止当前生成、把那个调用**直接当成模型的回答**返回（不再花第二轮）。

### 6.6 翻译兜底：换个模型补救，但不放大权限

一轮只在**已经失败**的路径上最多花：一次格式纠正 → 一次翻译（另一台免费模型，走仅对话通道，20 秒预算，材料**不截断**）→ 一次带诊断的重发。翻译结果按接收方 schema 复核，**翻译永远不能放宽可执行范围**。检测路径永不翻译——检测必须量模型本身。

### 6.7 思考档位

只广告真能下发到的档位：OpenCode 的 `variants` 里带 `reasoningEffort` 的才算数。写进 WorkBuddy 的声明三种：不支持推理 / 支持但无档位（勾选推理、走默认模式、关不掉思考）/ 有档位（默认优先 `medium`）。请求侧：档位能映射就下发 variant；**支持推理但没有 variant 的模型，WorkBuddy 带的默认档位照收**（不报错）。

### 6.8 图片

只接受内联 `data:image/(png|jpeg|webp|gif);base64,...` 并做 base64 往返校验；远程 URL 与本地路径一律拒绝（否则等于把不可信 URL 变成宿主机上的读文件动作）。图片作为附件 part 附在消息上，正文留 `[Attached image: …]` 标记。

### 6.9 流式

开局先写 SSE 注释行占位，每 10 秒心跳；**信封校验通过前不发任何 content**。上游真的开始出内容时先发一个 `delta:{role:'assistant'}` 分片，最后发内容、`finish_reason`、可选 usage、`[DONE]`。

### 6.10 隔离运行时的获取

1. 先找托管运行时（`runtime/<版本>/opencode`，二进制自报版本必须等于目录名）；
2. 再找本机已装的（`~/.opencode/bin`、Homebrew、Windows 的 npm 全局），复制进托管目录；`.cmd/.bat/.ps1` 明确拒绝；同版本已存在就不重写；
3. 查 `registry.npmjs.org` 的 `latest`：元数据必须包名对、版本号形状对、`dist.integrity` 是 sha512、tarball 域名在注册表列表里且路径以 `/<包>/-/` 开头；
4. 本机版本 ≥ 官方就复用；旧了才下载，下载走 sha512 校验、只解出那一个二进制、落盘后复验版本；
5. 官方源不可达时用 `registry.npmmirror.com`；官方元数据可用时镜像 tarball 必须匹配官方校验值；
6. 系统代理连不上 → 回退直连并通知上层；查不到官方版本但本机有可用运行时 → 直接用本地。

启动隔离：环境变量**白名单复制**（不带任何其它 provider 的 key）、四个 XDG 目录指向数据目录、随机 24 字节口令 + Basic 认证、启动前先 `models opencode --refresh --pure` 刷一次目录；就绪判据是健康检查返回 healthy **且版本与二进制自报一致**。

### 6.11 Windows 配置查找

模型只准用 `glob/list`（`*: ask` + 逐项 deny 其它），另一条监视器把所有审批**一律拒绝**并附只读说明。**只接纳真的执行过 glob 的路径**（模型正文里编出来的不算证据）；本地再做一次**只跟目录、不读内容**的补漏遍历（跳过 node_modules/.git/回收站，不跟随符号链接）；合并后校验：目录名像 WorkBuddy，或文件里已有自定义模型条目。多份候选按**校验读取之前的访问时间**取最新。

## 八、已知边界

- 免费模型与额度由上游决定，随时可能变化；「不可用」只代表**这一次没通过检测**。
- 系统代理只支持手动 HTTP/HTTPS，不支持 PAC/SOCKS。
- WorkBuddy 自己在运行时也会写 `models.json`。若你刚在 WorkBuddy 里保存过模型，最稳的顺序是：退出 WorkBuddy → 在 OC Ferry 点导入 → 再打开 WorkBuddy。
- 退出 OC Ferry 会把自己导入的条目摘掉（这是设计如此），所以那些模型可用期间请让它在托盘常驻。
